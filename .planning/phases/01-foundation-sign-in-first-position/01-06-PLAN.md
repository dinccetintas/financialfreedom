<objective>
Find a stock, add it once, and know exactly which listing it is.

**User story:** **As a** family member recording what I own, **I want to** search for a stock by ticker or company name and add it, **so that** my transaction points at the right listing on the right exchange and not at a bare ticker that could mean two different companies.

This is the expansion that makes ROADMAP success criterion 5 demonstrably true rather than nominally satisfied. The tracer created the `instruments` table with `unique(exchange_mic, symbol)` and a partial unique ISIN index; this plan fills it with real, enriched rows — and, critically, keeps the ledger writable when the outside world is not.

D-15 is the load-bearing decision here: recording a real transaction must never be blocked by an external service being down. The ledger is the source of truth; Finnhub is not. So every failure path in this plan ends at "the user hand-creates the instrument and the row is marked for later enrichment", never at an error dialog.

D-13 puts the lookup behind a `SymbolSearchProvider` interface specifically so this choice stays reversible — and so that Phase 3's BIST end-of-day price-provider spike (EODHD vs Twelve Data) remains a separate, unprejudiced decision.

Purpose: INST-03 and the enrichment half of INST-01.
Output: search, enrich, add, and a manual path that always works.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → `searchInstruments` / `addInstrument` server actions | Untrusted free-text query and untrusted manual instrument fields cross here |
| Next.js server → Finnhub API | An API key leaves the system in a request header; a third-party response enters as data |
| Next.js server → OpenFIGI API | A third-party response enters as data and is written into shared, non-tenant-scoped reference rows |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-26 | Information Disclosure | `FINNHUB_API_KEY` reaching the browser bundle | high | mitigate | `src/lib/instruments/finnhub.ts` imports `server-only`, so a client-component import fails the build rather than shipping the key |
| T-01-27 | Tampering | Third-party Finnhub/OpenFIGI response written into shared `instruments` rows | high | mitigate | Every provider response is parsed through the same Zod `addInstrumentSchema` as manual input before any insert; nothing from a response is trusted as-is, and `instruments` writes require an authenticated session |
| T-01-28 | Denial of Service | OpenFIGI 429 or Finnhub outage blocking instrument creation and therefore transaction entry | medium | mitigate | Every enrichment failure resolves to a typed status and the insert proceeds with `enrichment_status: 'failed'`; requests are batched at 10 jobs per POST; the manual path (D-15) is always available |
| T-01-29 | Spoofing | A user adding a fabricated `exchange_mic`/`symbol` pair into shared reference data | medium | mitigate | `exchangeMic` is constrained to `^[A-Z0-9]{4}$` and the row is stored `unenriched`, so it is visibly marked as not fully identified rather than presented as an authoritative listing. | T-01-30 | Tampering | Injection through the free-text search query into the outbound provider URL | medium | mitigate | The query is Zod-validated and passed via `URLSearchParams`, never string-concatenated into the URL |
| T-01-31 | Information Disclosure | Provider error bodies surfaced to the user revealing key or endpoint details | low | mitigate | The UI renders only the fixed documented fallback copy; raw provider errors are logged server-side without the key and never returned to the client |

**ASVS level:** 1 (V5 Input Validation primarily, V4 for the session requirement on reference-data writes). **Blocking threshold:** high — both high-severity threats carry `mitigate` dispositions with build-time or test-time enforcement.

## Planner Assumptions (flagged — not silently dropped)

- **UI consideration — partial, instrument search results (⚠ unresolved in `01-UI-SPEC.md`).** Behavior when Finnhub returns a company match with no resolvable `exchange_mic` is not specified. Assumption carried into Task 1: such a result is **dropped from the mapped list**, so it is treated as a no-match and the user falls through to the manual-entry path (D-15) where they supply the MIC themselves. The alternative — surfacing the match with a null `exchange_mic` — was rejected because it would let a row be created that violates the INST-01 identity intent while still satisfying the nullable column. If the developer prefers surfacing such matches with a "pick the exchange" step, that is a UI addition, not a schema change.
