<objective>
Make a backdated transaction's frozen FX rate sourceable from day one.

**User story:** **As a** family member entering a purchase I made three years ago, **I want** the system to already know what the lira was worth that day, **so that** my cost basis is frozen at the real historical rate rather than at today's.

`transactions.fx_rate_to_base` is snapshotted at write time and never recalculated — that is what makes a historical report reproducible instead of silently rewritten every day the FX table updates. But a frozen rate is only correct if there is a rate to freeze. Phase 1 is USD-only by its own success criteria, so no Phase 1 transaction actually needs a TRY rate; what Phase 1 owes the project is the **data** being in place and the **direction convention** being fixed before the first row that depends on it exists.

D-05 draws the scope line precisely: Phase 1 ships a **script**, not a job. The scheduled EVDS sync, gold rates and the full DATA-02/DATA-03 integration are Phase 5. Nothing in this plan may create a cron entry or a recurring trigger.

Purpose: populate `fx_rates` with authoritative history and fix the direction convention that `PITFALLS.md` §5 and `PROJECT.md`'s Key Decisions both call out as a classic silent-wrongness source.
Output: a TCMB client, an idempotent backfill script, and a read helper that cannot be mistaken for a same-day lookup.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Developer machine → TCMB EVDS API | An API key leaves in a request header; a third-party response enters as data |
| Backfill script → `fx_rates` (global, non-tenant-scoped) | Shared reference data every future valuation and cost-basis figure depends on is written here |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-32 | Tampering | An unparsed or wrongly-oriented TCMB response silently inverting every future cost basis | high | mitigate | The direction contract is named in the column identifier (`rate_quote_per_base`), stated at the file head, and pinned by a reciprocal test against a captured fixture; the parse rejects null/empty values instead of coercing them to zero |
| T-01-33 | Tampering | A re-run overwriting historical rates and making an already-frozen cost basis irreproducible | high | mitigate | `on conflict … do nothing`, asserted by an idempotency test that checks stored values as well as row counts |
| T-01-34 | Information Disclosure | `TCMB_EVDS_API_KEY` leaking through a URL, a log line or a shell history entry | medium | mitigate | The key is sent as an HTTP header, never a query parameter; a test asserts it is absent from the request URL; the script never echoes it |
| T-01-35 | Denial of Service | A multi-year range timing out or exceeding the response size limit and writing a partial series unnoticed | medium | mitigate | Requests are chunked to at most one year each; the script reports returned-day and inserted counts, and exits non-zero on an empty weekday-containing range rather than silently writing nothing |
| T-01-36 | Repudiation | A carried-forward rate presented as a same-day rate | medium | mitigate | `getRateOnOrBefore` returns the source date alongside the rate, so a caller cannot present the value as same-day without discarding information the type hands them |

**ASVS level:** 1 (V5 Input Validation for the third-party response boundary). **Blocking threshold:** high — both high-severity threats are integrity concerns with `mitigate` dispositions backed by pinned tests.
