<objective>
Close the auth loop the tracer left open: nobody can register, everybody can recover, and nobody keeps a password the seed script chose for them.

**User story:** **As a** family member who has forgotten my password, **I want to** get a reset link by email and set a new one, **so that** I am never locked out of my own portfolio — and **as** the person who set the system up, **I want** each of the other three to choose their own password on first sign-in, **so that** the temporary one I generated never becomes their real one.

This is an expansion on the proven slice, not a new architecture: the session, the Better Auth instance and the `(auth)` route group already exist. What changes is one config object, one email integration, and one server-side gate.

`01-RESEARCH.md` Pitfall 2 is the reason this plan exists as its own unit: **Better Auth has no built-in forced-password-change**. Its own issue tracker carries that as an open feature request. D-08's flow is real application code — a `mustChangePassword` field plus a layout gate — not a config flag, and if the planner assumed otherwise no task would exist for it and the feature would silently not ship.

Purpose: satisfy AUTH-02 and the literal reading of AUTH-04 ("no public registration surface exists").
Output: reset-by-email, a closed registration surface proven by test, and a first-login password gate.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → forgot-password / reset-password routes | Unauthenticated, publicly reachable input crosses here, including a bearer-equivalent reset token |
| Next.js server → Resend API | A reset URL containing a single-use token leaves the system |
| Session cookie → dashboard layout gate | A partially-provisioned account (temporary password) attempts to reach real data |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-01-13 | Information Disclosure | Reset-token leakage via server logs or a Referer header | high | mitigate | The reset URL and token are never passed to any logger; the reset route sets a `no-referrer` referrer policy and makes no third-party requests. - **AUTH-02 (unresolved, unclassified in the edge probe).** Assumption: the reset link's lifetime is Better Auth's default (approximately one hour), the token is single-use, and requesting a second reset invalidates the first.
