<objective>
Sharing that a family member can actually take back.

**User story:** **As** a portfolio owner, **I want to** let a specific family member view one of my portfolios and take that access away again, **so that** I can show my father his own holdings without opening my entire account to him permanently.

D-11 makes `portfolio_shares` and the RLS predicate that reads it non-optional — they were already built in the tracer, because the single access predicate at `ARCHITECTURE.md:330` implements private-by-default and opt-in sharing in one place. What was genuinely open was the UI, and a plain grant/revoke control is what closes AUTH-07 honestly. This plan adds that control and proves the two directions of the guarantee: a grant makes rows visible, and a revoke makes them invisible again.

Per D-12 the `permission` column is typed `text CHECK (permission IN ('read','write'))` exactly as `ARCHITECTURE.md:111` specifies, but the Phase 1 UI only ever grants `'read'`. Write-sharing raises a ledger-attribution question — when the owner enters a transaction into a parent's portfolio, is `created_by` the actor or the portfolio owner? — that Phase 2 is better placed to answer alongside bulk entry. The schema needs no migration when that answer arrives.

Purpose: AUTH-07 and AUTH-08, plus the exactly-once invariant that the assumption-delta decision in `01-02-PLAN.md` committed to.
Output: grant, revoke, and a database-level proof that both work.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Grantee session → shared portfolio | A second real user legitimately reads another user's tenant rows; the boundary is the grant itself |
| Browser → grant/revoke server actions | A portfolio id and a target user id cross here from an untrusted client |
| Next.js cache → former grantee | A rendered or cached payload can outlive the grant that authorized it |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-21 | Elevation of Privilege | `grantPortfolioShare` called by a non-owner or by a grantee | high | mitigate | Explicit ownership assertion inside the same `withUserScope` transaction as the insert, because the OR'd read policy lets a grantee *see* the portfolio row; asserted by `tests/portfolios/sharing-actions.test.ts` and at the SQL layer by the grantee-re-share case |
| T-01-22 | Elevation of Privilege | A `permission: 'write'` value smuggled into the grant action | high | mitigate | `permission` is not an input field at all; the server writes the literal `'read'`. The CHECK constraint remains as the schema-level backstop (D-12) |
| T-01-23 | Information Disclosure | A revoked grantee still served the portfolio from a cached render or an open session | high | mitigate | Tag-based plus path-based revalidation on revoke, and a database-level assertion that a scope spanning the revoke also returns zero rows.
