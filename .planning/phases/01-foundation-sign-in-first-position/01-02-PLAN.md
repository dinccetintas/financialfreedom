<assumption_delta_decision>
The `assumption-delta scan` fired on this phase with a `pluralization` signal: *"a **second** family member's session returns zero rows for the first user's portfolio and transactions unless explicitly shared."*

- **Noun that is now primary:** the **portfolio principal** — any user who may read a portfolio, whether by ownership or by an explicit share grant. "Owner" is demoted to one of two variants of principal, not the primary identity for access.
- **Decision:** `promote`. Access is expressed as a **single RLS predicate** on `portfolios` that evaluates ownership and share-grant membership together (`owner_user_id = :me OR id IN (SELECT portfolio_id FROM portfolio_shares WHERE shared_with_user_id = :me)`), and every other tenant table derives visibility from that one predicate through its denormalized `portfolio_id`. Sharing is not a second check bolted alongside an owner check that application code must remember to also run.
- **Rationale:** `ARCHITECTURE.md:330` already specifies exactly this shape, and D-11 makes `portfolio_shares` non-optional precisely because the RLS predicate reads it. Adding sharing alongside a still-primary owner check is the failure mode this promotion prevents: a query path that consults ownership only would silently return zero shared rows with no error.
- **Invariant test (accepted, scoped into `01-05-PLAN.md`):** a portfolio the user both owns *and* holds a share grant for appears **exactly once** in a scoped `SELECT`. That assertion goes red the instant a future phase reintroduces a join-based policy that duplicates the row, or a second owner-only code path.
</assumption_delta_decision>
