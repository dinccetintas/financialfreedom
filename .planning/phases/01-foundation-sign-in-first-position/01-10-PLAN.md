<objective>
Everything recorded, in an order that never shuffles, with nothing hidden without saying so.

**User story:** **As a** family member, **I want to** see every transaction in a portfolio and filter and sort it, **so that** I can find the entry I am looking for and confirm the whole record is what I think it is.

This closes ROADMAP success criterion 2's second half. It also closes the loop D-17 opened: the list defaults to the **netted view** — corrected values shown, superseded rows hidden — because success criterion 3 requires the original stay "visible in history", not that it clutter the default view, and because Phase 2 will multiply row counts. That default is only honest if the user can always see what it is hiding, which is why a per-row history expansion and a list-level raw-ledger toggle ship in the same plan as the netting.

Sort determinism matters more here than it looks. Trade date has low cardinality — a family member entering a historical portfolio will produce many rows sharing one date — so a sort keyed on date alone reshuffles rows on every reload. The order is therefore total: date, then `created_at`, then `id`.

Purpose: LEDG-10, and the visibility half of LEDG-06.
Output: a filterable, sortable, paginated transaction list with an always-reachable raw ledger.
</objective>

  <behavior>
    - `listTransactions({ portfolioId, view: 'netted' })` omits both the superseded original and its voiding row, and includes the replacement row carrying the corrected values.
    - `listTransactions({ portfolioId, view: 'raw' })` includes every row: original, void and replacement.
    - Both views return rows ordered by `trade_date` descending, then `created_at` descending, then `id` — a total order. Ten rows sharing one `trade_date` return in the identical sequence across twenty consecutive calls.
    - Every selectable sort (date, instrument symbol, quantity, price, total) falls back to the same `created_at` then `id` tie-break, so re-sorting on a low-cardinality column does not reshuffle equal rows.
    - A portfolio with zero transactions returns `{ rows: [], total: 0, hiddenCount: 0 }` — an empty result, never null and never an error.
    - The result carries `total` (all rows in the selected view), `page`, `pageSize` (50) and `hiddenCount` (rows excluded by netting plus rows beyond the current page), so the UI can state exactly what is not on screen.
    - Every monetary and quantity value is returned as a string; no value passes through the JavaScript number type.
    - The query runs inside `withUserScope`; a user with no grant on the portfolio receives zero rows, asserted with the application-layer check bypassed.
    - Page 2 of a 137-row list returns rows 51-100 with no row appearing on two pages and none skipped, verified by collecting all pages and asserting the id set equals the full set exactly once.
  </behavior>

    Create `src/lib/ledger/list-transactions.ts` exporting `listTransactions` and the `TransactionListView` type. Inside `withUserScope`, it joins `transactions` to `instruments` and:
    - **Netted projection:** excludes rows that are pointed at by some row's `voids_transaction_id` (superseded originals) and excludes rows whose own `voids_transaction_id` is not null (the voiding rows themselves). What remains is exactly the set of currently-effective entries.
    - **Raw projection:** excludes nothing and tags each row `original`, `void`, `replacement` or `current`, reusing the classification from `src/lib/ledger/history.ts`.
    - Orders by the selected sort column, then always `created_at desc, id asc`. Express the tie-break once as a shared order-by fragment so a new sort column added in a later phase cannot omit it.
    - Paginates at 50 rows and returns `total`, `page`, `pageSize` and `hiddenCount`. `hiddenCount` is the count of rows the selected view and the current page together exclude — it is what the UI's hidden-rows disclosure renders, so it must be computed, not estimated.

    Add a file-head note stating the total-order contract in one sentence and why it exists: trade date is low-cardinality in this application, so any order not tie-broken to a unique column reshuffles rows between reloads.

    Write `tests/ledger/list-transactions.test.ts` FIRST, one named case per behavior bullet. The order-stability case runs the query twenty times over ten same-date rows and asserts an identical id sequence each time. The pagination case asserts set equality across all pages.

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-01-51 | Tampering | A client-supplied sort column interpolated into the ORDER BY clause | high | mitigate | `sort` is a Zod enum mapped to a fixed set of Drizzle column references; no user-supplied string ever reaches raw SQL |
