<objective>
The first real economic fact in the ledger.

**User story:** **As a** family member, **I want to** record that I bought 10 shares of a US stock on a date at a price with a fee, **so that** the system holds what I actually own instead of what I roughly remember.

This is the expansion that turns the walking skeleton into the thing the phase is named after. Every architectural piece it needs already exists and is proven: the `transactions` and `lots` tables with their CHECK constraints, the RLS policy, the decimal boundary module, the instrument identity. What this plan adds is the validated writer, the form, and the derived-position read.

Two rules govern every line of it. First, **append-only**: this writer only ever inserts; nothing in it updates or deletes a `transactions` row, because corrections are new rows (that is `01-09-PLAN.md`). Second, **decimal end to end**: values arrive as strings, are validated as decimals, are persisted at the column's declared scale, and are read back as strings — no monetary value is ever routed through the JavaScript number type, at any boundary, including JSON serialization to the browser.

Purpose: LEDG-01, plus LEDG-07's derived-position read.
Output: a buy transaction that appears as a position.
</objective>

  <behavior>
    - A valid buy produces exactly one `transactions` row (`type: 'buy'`) and exactly one `lots` row, inserted in the same database transaction; if the lot insert fails, no transaction row remains.
    - The `lots` row's `quantity_opened` and `quantity_remaining` both equal the transaction's quantity, and `opened_by_transaction_id` points at the new transaction row.
    - `quantity: '0'` is rejected; `quantity: '-1'` is rejected; `quantity: '0.00000001'` is accepted (the smallest value at the declared 8-decimal scale).
    - `price: '0'` is accepted; `price: '-0.0001'` is rejected. `feeAmount: '0'` is accepted; `feeAmount: '-0.01'` is rejected.
    - Omitting `feeAmount` entirely stores `'0'`, not null.
    - `quantity: '10.12345678'` persists and reads back byte-identically as `'10.12345678'` — no rounding at write time.
    - `price: '123.45678'` (five decimals, past the declared 4-decimal money scale) is rejected by the schema before reaching the database, with a field-level error naming the maximum scale — the write path never relies on the database silently truncating.
    - `fxRateToBase` is stored as `'1'` for a USD price currency in a USD-base portfolio; the column is never left null.
    - `denormalized portfolio_id` on both the transaction and the lot equals the account's portfolio, so the RLS predicate has something to match.
    - A buy against a portfolio the acting user neither owns nor is granted a share of is rejected — asserted with the application-layer ownership check removed, so the rejection is proven to come from RLS.
    - An `instrumentId` that does not exist is rejected by the foreign key, surfaced as a field-level error rather than an unhandled exception.
    - No `UPDATE` or `DELETE` statement against `transactions` appears anywhere in this module.
  </behavior>

Each refinement carries the documented error copy pattern: "Quantity must be greater than zero.", "Price can't be negative.", "Pick a date for this transaction." It derives the acting user from `requireSession()`, validates with `buyTransactionSchema`, resolves the account's `portfolio_id`, computes `fx_rate_to_base` — `'1'` when `priceCurrency` equals the portfolio's `base_currency`, otherwise looked up through `getRateOnOrBefore` for the trade date and stored with the source date recorded in `fx_rate_source` — and then, inside a single `withUserScope` transaction, inserts the `transactions` row and the opening `lots` row. `cost_basis_per_unit_local` is `price`; `cost_basis_per_unit_usd` is `price` multiplied by `fx_rate_to_base` computed with `decimal.js` and rendered with `toNumericString`. <threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → `addBuyTransaction` server action | Untrusted portfolio id, account id, instrument id and decimal strings cross here |
| Server action → `transactions` / `lots` (RLS-protected) | The first economic facts in the system are written here |
| Postgres NUMERIC → JSON → browser | Precision is lost silently at this boundary if a value is coerced to a JavaScript number |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-37 | Elevation of Privilege | A client-supplied `portfolioId` or `accountId` pointing at another family member's portfolio | critical | mitigate | The write runs inside `withUserScope` with the user id from `requireSession()`; the RLS policy rejects the insert. Proven by the test that bypasses the application-layer ownership check and still observes rejection |

| T-01-39 | Tampering | An over-scale or out-of-range value relying on the database to silently truncate | high | mitigate | Scale and range are enforced by Zod before the write, with the CHECK constraints as the independent database backstop; the over-scale case asserts a schema rejection rather than a database error |

## Planner Assumptions (flagged — not silently dropped)

- **LEDG-07 (unresolved, unclassified in the edge probe).** Assumption: "positions are derived from the ledger and can be rebuilt from scratch at any time" is satisfied in Phase 1 by a **live grouped query** over `lots`, with **no `positions_snapshot` table** in migration 001. Reasoning: D-01's approved table list does not include `positions_snapshot`; there is no price data in Phase 1 to value a snapshot against; and a function that stores nothing is rebuildable by construction rather than by a rebuild job. `01-RESEARCH.md` Open Question 1 reaches the same recommendation and asks that the reasoning be flagged explicitly so it is not later mistaken for an oversight — this is that flag. Phase 3 may add a precomputed snapshot as a cache in front of `derivePositions` without changing its contract. What is **not** assumed and remains genuinely open: whether "rebuildable" should also be demonstrated by an explicit rebuild command in a later phase, once a snapshot table exists to rebuild.
