<objective>
Turn the two claims Phase 1 cannot afford to get wrong — tenant isolation and decimal money — from assertions in a document into tests that fail loudly.

**User story:** **As a** family member, **I want to** know that nobody else can see my portfolio and that no number I entered was silently rounded, **so that** I can trust every figure the system will later compute from it.

The tracer proved the happy path once. This plan proves the guarantees hold in the cases that actually break them: an unset session variable, a value one digit past the declared scale, two decimals that differ only in trailing zeros, and the same ticker listed on two exchanges. `01-RESEARCH.md` Assumption A3 is explicit that the `set_config` + `@neondatabase/serverless` combination was verified from docs and not hands-on tested — the isolation test here is the verification.

Purpose: `01-VALIDATION.md` names `tests/db/rls-isolation.test.ts` "the single most important test in this phase". D-07 requires the float guard be a CI-enforced mechanism, not a convention, precisely so it catches the mistake in Phase 7 or in an agent-authored migration in Phase 12.
Output: four database-level test files, the decimal boundary module every later plan imports, and a CI workflow that runs them.
</objective>

  <action>
    Create `tests/db/rls-isolation.test.ts`. It runs against the real Neon test branch — never a mocked driver, because a mock cannot prove a Postgres policy.

    Fixture: seed two users (`userA`, `userB`) through the same path `scripts/seed-family-users.ts` uses. Under `userA`'s scope create one portfolio, its default account, one instrument reference row, one `transactions` row, one `lots` row and one `lot_closures` row so every RLS-protected table has a row to be invisible.

    Assert, each with `tx.execute(sql\`select …\`)` raw statements rather than through application query helpers, so the proof is at the policy layer:
    - **Cross-tenant:** inside a transaction whose `app.current_user_id` is `userB`, `select count(*)` returns 0 for each of `portfolios`, `accounts`, `transactions`, `lots`, `lot_closures`, `portfolio_shares`.
    - **Fails closed:** inside a transaction where `app.current_user_id` is never set at all, the same six counts are 0 — the policy must default-deny, never default-open. Repeat with the setting explicitly set to the empty string, which must also yield 0 rows and must not raise an invalid-uuid error (this is what the `nullif(...)` in the policy predicate is for).
    - **Own rows still visible:** inside `userA`'s scope the same six counts are non-zero, so the isolation assertions are not vacuously passing on an empty database.
    - **Global tables stay readable:** inside `userB`'s scope, `select count(*) from instruments` and `from market_calendar` are both greater than 0 — reference data is deliberately not tenant-scoped and this test documents that as intentional.
    - **Scope does not leak across transactions:** run `userA`'s scoped transaction, let it commit, then immediately run a bare `select count(*) from portfolios` outside any `withUserScope` on the same pooled client and assert 0. This is the concrete detection for the leaked-session-variable failure mode described in `01-RESEARCH.md` Pitfall 1, whose signature is intermittent rather than consistent.
    - **Interleaved scopes:** run two `withUserScope` calls concurrently with `Promise.all`, one per user, each asserting it sees only its own portfolio count. Repeat the pair ten times to give a recycled-connection leak a chance to surface.
  </action>

  <action>
    Create `src/lib/money/decimal.ts` as the single sanctioned decimal boundary for the whole project, exporting:
    - `toDecimal(value: string): Decimal` — constructs from a string only; the parameter type is `string`, never `number`, so a float cannot enter by accident.
    - `toNumericString(value: Decimal, scale: number): string` — renders for persistence at the column's declared scale using `Decimal.ROUND_HALF_UP`, returning a plain string.
    - `formatUsd(value: string): string` — display only: `$` prefix, thousands comma grouping, exactly 2 decimals.
    - `formatQuantity(value: string): string` — display only: up to 4 decimals with trailing zeros trimmed, so `10` renders as `10` and `12.5` as `12.5`.
    Configure `Decimal.set({ precision: 40, rounding: Decimal.ROUND_HALF_UP })` once at module load. Add a file-head note stating the rule this module exists to enforce: monetary values stay strings from the Postgres driver through the server action and the JSON boundary to the browser, and are only turned into a `Decimal` for arithmetic or formatting — they are never routed through the JavaScript number type.

    Create `tests/db/money-types.test.ts` — the D-07 guard. Query `information_schema.columns` for `table_schema = 'public'` and fail with the offending `table_name.column_name` list if any column whose name matches `%money%`, `%price%`, `%quantity%`, `%rate%`, `%amount%`, `%basis%`, `%value%`, `%fee%` or `%cost%` has `data_type` in (`real`, `double precision`). Assert positively as well: `transactions.price`, `transactions.fee_amount` and `lots.cost_basis_per_unit_usd` have `numeric_precision` at least 19 and `numeric_scale` at least 4; `transactions.quantity` and `lots.quantity_remaining` have `numeric_precision` at least 28 and `numeric_scale` at least 8; `fx_rates.rate_quote_per_base` and `transactions.fx_rate_to_base` have `numeric_scale` at least 10.

    Create `tests/db/decimal-roundtrip.test.ts`:
    - Insert a set of hostile literals as strings through Drizzle — `0.1`, `0.2`, `1234567890123.4567`, `0.00000001`, `99999999999999.9999` — into a scratch transaction row under a scoped transaction, select them back, and assert `toDecimal(returned).eq(toDecimal(original))` for each. Also assert `typeof returned === 'string'`, documenting the driver behaviour Pitfall 5 depends on: the driver returns NUMERIC as a string on purpose.
    - Assert `toDecimal('1.50').eq(toDecimal('1.5'))` is true while `'1.50' === '1.5'` is false, and that Postgres agrees by selecting `'1.50'::numeric = '1.5'::numeric`.
    - Assert boundary behaviour: a `price` value with exactly 4 decimal places inserts successfully; a value with 5 decimal places does not silently truncate — capture whichever behaviour the column actually produces (error or rounding) and assert it explicitly, so the contract is pinned rather than assumed.
    - Assert `fee_amount` defaults to `'0'` when omitted from an insert, and that selecting it back yields a non-null string.
    - Assert `toNumericString(toDecimal('2.005'), 2)` returns `'2.01'`, pinning ROUND_HALF_UP, and that no rounding happens on the persistence path for values already inside the declared scale.
  </action>
