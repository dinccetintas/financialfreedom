<objective>
Correcting a mistake without erasing it.

**User story:** **As a** family member who typed 100 shares instead of 10, **I want to** fix it, **so that** my position is right — and **as** the person who will one day audit this, **I want** the original entry still there, **so that** I can see what was recorded and when it changed.

D-17 fixes the mechanism: an edit is **void + reissue, two new rows**. The correcting row sets `voids_transaction_id` to the original; a replacement row carries the corrected values. The original is never mutated or deleted. This is rated one-way in `01-CONTEXT.md` and was approved in `01-01-PLAN.md`: the ledger's correction semantics are the foundation the audit log (Phase 12), the returns engine (Phase 6) and corporate actions (Phase 5) all build on — changing the shape later invalidates every derived projection.

A naming reconciliation, stated once so nothing downstream guesses: the edge-coverage report refers to this relationship as `supersedes_id`. The canonical column in this project is `transactions.voids_transaction_id` (`ARCHITECTURE.md:176`, D-17), and its partial unique index `transactions_voids_key` — created in migration 001 — is what makes "a row cannot be superseded twice" a database guarantee rather than an application-layer hope.

Purpose: LEDG-06, and the correction half of ROADMAP success criterion 3.
Output: correct, remove, and a viewable history chain.
</objective>

  <behavior>
    - `voidTransaction(originalId)` inserts exactly one new `transactions` row whose `voids_transaction_id` is the original id, and leaves the original row byte-identical — asserted by comparing every column of the original before and after.
    - `correctTransaction(originalId, correctedFields)` inserts exactly two new rows: the voiding row and a replacement row carrying the corrected values. The original is unchanged. Total row count for that instrument goes from 1 to 3.
    - The voiding row carries no new economic fact: its `quantity` is null (or the schema's designated no-economic-effect value) and it does not open a lot.
    - The replacement row opens its own lot; the voided original's lot has `quantity_remaining` set to `'0'` in the same database transaction, so `derivePositions` nets correctly without any recomputation job.
    - Correcting an already-corrected row is rejected by `transactions_voids_key`, surfaced as a typed "already corrected" result rather than an unhandled constraint error. Assert on the index name in the caught error.
    - Two concurrent `correctTransaction` calls against the same original: exactly one succeeds and one fails on the unique index. Assert both outcomes explicitly — never both succeeding, and never the original being mutated by either.
    - A double-submit of the same correction (the same original id twice in quick succession) produces exactly one voiding row, which is the same guarantee expressed from the UI's perspective.
    - `correctTransaction` on a transaction in a portfolio the acting user cannot write to is rejected by RLS, asserted with the application-layer check bypassed.
    - After correcting a buy from 100 to 10 shares, `derivePositions` reports exactly `'10'` for that instrument.
    - After `voidTransaction` on the only buy of an instrument, that instrument no longer appears in `derivePositions` at all.
  </behavior>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → `correctTransaction` / `voidTransaction` server actions | An untrusted transaction id and untrusted corrected values cross here |
| Concurrent requests → `transactions` | Two requests can race to supersede the same row |
| Correction path → derived positions | A correction that does not net out leaves the user with a wrong holding and no error |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-44 | Repudiation | An original transaction mutated or deleted, destroying the record of what was entered | critical | mitigate | Neither ledger writer contains an update or delete against `transactions`; the unchanged-original assertion compares every column before and after; the only permitted update targets `lots.quantity_remaining` |
| T-01-45 | Tampering | A double-submit or a race creating two reversing entries for one original, double-counting the correction | high | mitigate | The partial unique index `transactions_voids_key` from migration 001 is the primary control, not an application pre-check that would lose the race; asserted by the `Promise.allSettled` concurrency case that requires exactly one fulfilled and one rejected |
| T-01-46 | Elevation of Privilege | Correcting a transaction in a portfolio the acting user cannot write to | high | mitigate | Both writers run inside `withUserScope`; the RLS-rejection case is asserted with the application-layer check bypassed |
| T-01-47 | Tampering | A correction that changes the ledger but not the derived position, leaving a silently wrong holding | high | mitigate | The void sets the original lot's `quantity_remaining` to `'0'` in the same database transaction as the voiding insert; `tests/ledger/positions.test.ts` is re-run as part of this plan's verify to prove the netting |
| T-01-48 | Repudiation | A correction with no recorded actor | medium | mitigate | `created_by` on both new rows comes from `requireSession()` and is not an input field |
| T-01-49 | Tampering | The correct dialog validating differently from the buy path, admitting a value the buy path would reject | medium | mitigate | `correctTransactionSchema` composes `buyTransactionSchema`'s field definitions, and the replacement insert goes through the same shared helper as `addBuyTransaction` |

**ASVS level:** 1 (V4 Access Control, V5 Input Validation). **Blocking threshold:** high — the one critical and three high threats all carry `mitigate` dispositions backed by database-level guarantees rather than application-layer conventions.
